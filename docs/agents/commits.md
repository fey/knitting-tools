# Коммиты

**В `main` PR уходит squash-мержем, и коммитом там становится его заголовок** — тело коммита
пустое, коммиты ветки в `main` не доезжают. Других способов мержа в репозитории нет, они
выключены. Поэтому всё правило ниже — про **заголовок PR**; коммиты внутри ветки пишутся
в том же виде по привычке, и хук их проверяет, но в историю и в заметки они не попадают.

Заголовок — [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/): тип
по-английски, описание по-русски, обычным предложением с заглавной и без точки.

```
feat: Отметка текущего ряда на схеме (#9)
fix: Разбор ссылки чинится дефолтом, а не подтягиванием (§10.4)
docs: Таблицы размеров носков — исследование
```

Из этих заголовков release-please собирает заметки к релизам (`docs/agents/release.md`). Их читает
мастер, а не разработчик.
Поэтому тип выбирают по тому, **заметит ли правку человек на странице**:

| Тип | Когда | В заметки к релизу |
|---|---|---|
| `feat` | на странице появилось новое: поле, кнопка, режим, раздел | да |
| `fix` | страница вела себя не так, как обещает спека, — теперь так | да |
| `perf` | страница стала быстрее, а поведение то же | да |
| `refactor` | код переложен, на странице ничего не изменилось | нет |
| `test` | только тесты и базлайны | нет |
| `docs` | спека без смены поведения, README, research, прототипы в `.scratch/` | нет |
| `build`, `ci` | зависимости и сборка; `.github/workflows/` | нет |
| `chore` | всё прочее служебное: хуки, конфиги | нет |

- **Описание у `feat`, `fix` и `perf` — про экран, словами мастера**: что стало видно или как
  теперь ведёт себя страница. «Сантиметры на схеме и в «Итоге»», а не «Пропс gauge в ChartGrid».
  Словарь — из §2 спеки, пол того, кто вяжет, не угадывается (CLAUDE.md, «Язык»).
- **`!` после типа — правка ломает то, на что мастер уже опирается**: старые ссылки с hash
  открывают не тот расчёт, отмеченный прогресс в `localStorage` теряется. Что именно сломалось —
  в теле, строкой `BREAKING CHANGE: …`.
- **Один PR — одна запись в заметках.** PR, который и добавляет возможность, и чинит в ней
  найденное до мержа, — это `feat`. `fix` — только на то, что уже лежит на живой странице:
  починка невыпущенного в заметках звучала бы как исправление того, чего мастер ещё не видел.
- **Два изменения, которые мастер заметит порознь, — два PR.** Если так уже не вышло, в описание
  PR перед мержем кладут блок, и release-please возьмёт записи из него, а не из заголовка:
  ```
  BEGIN_COMMIT_OVERRIDE
  feat: Первое изменение
  fix: Второе изменение (§7)
  END_COMMIT_OVERRIDE
  ```
- **Scope не ставится**, пока калькулятор один.
- Заголовок — до 100 символов.

Проверяет commitlint (`commitlint.config.js`) в двух местах. **Заголовок PR** — шагом прогона
на PR (`make lint-pr-title`): этот заголовок и уедет в `main`. Прогон заводится на открытие
PR и на push в ветку, а на правку заголовка — нет: переименовал PR — запушь или перезапусти
прогон. **Коммиты ветки** — хуком `commit-msg` из lefthook (`lefthook.yml`); хук ставится сам
на `make install`.
